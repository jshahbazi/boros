# Funded standing-policy rendering

October 5, 2026. The internal renderer prepares mandatory standing-policy text from an owner-private paid current-state proof. It is a prerequisite for the [shared authority gates](AUTHORITY-GATES.md). It does not enable managed GUI, provider, native, local-read or background consumers. Complete actual input/dependency proofs and consumer boundaries remain unfinished.

## Complete selected state

`AuthorityPolicyRenderer` uses the existing authority kernel's project/task resolution. It requires the accepted binding's exact store/owner, epoch, authority revision, active task/revision and conversation selection. Blocked conflicts refuse rendering. The selected IDs/revisions and complete resolution digest must match the accepted episode. Revoked, expired, proposed, scheduled, superseded and inapplicable policies are absent; a more specific selected policy follows the kernel's scope hierarchy. Compatible same-value records retain every selected ID/revision.

The message begins with the supplied host instructions, followed by a versioned host explanation and canonical JSON containing every selected policy record. Rules and values retain complete UTF-8 text. JSON provides field boundaries. No original source excerpt is interpolated as an instruction. The explanation records the intended host/current-task/standing-policy precedence and says that source references grant no permissions. This is structural provenance and deterministic rendering; it does not prove that an unrestricted model obeys the hierarchy.

The private manifest records its strictly decoded lower-only limits and binds the exact episode binding digest, project/task/revision, epoch/authority revision, standing-policy resolution digest, selected-record digest, complete selected policy references, host instruction digest and complete system-message digest/byte count. Exact canonical source spans are deduplicated and sorted by bytes. Global policy source spans keep their actual project/conversation scope. Canonically equivalent Unicode identifiers are distinct.

The standing-policy resolution digest is separate from `ProviderComponentProof.policyDigest`, which hashes the frozen context resource-cap policy. The supplied host instruction bytes are recorded as input consistency evidence. Their hash does not authenticate a trusted host or replace the future complete input proof.

## Bounds and funding

The lower-only encoded ceilings are 128 KiB for the complete system message, 128 KiB for selected-policy JSON, 256 selected policies and 512 unique source spans. Individual policy values retain the authority kernel's 8 KiB bound. Each selected record's encoding and cumulative JSON length are checked before the complete selected array is encoded. Complete message framing and the supplied host instructions count toward the system limit. Overflow rejects the whole preparation; there is no truncation, omitted selected policy or increased original allowance. These limits do not estimate tokenizer use or physical heap size.

`MemoryStore.renderManagedPolicy` requires the original owned lease and an existing funded validation session. It reads no fresh source payload. Scalar sizing comes from the already paid private proof; the source journal and cache witnesses remain responsible for source-byte integrity. Before the eligibility callback, a separate internal `authorityValidation` reservation and arm commit a render charge under the original episode's nine resource caps:

- One memory operation.
- Logical raw-byte ceiling: twice the bounded current-state encoding, supplied host UTF-8 bytes, twice the full-system ceiling and twice the selected-policy ceiling.
- Metadata ceiling: 64 logical visits per policy in the paid current state, four per task, two per conversation binding, twice the bounded possible source-span count, four per bounded possible selected policy and 256 fixed bookkeeping rows. The selected count ceiling is the smaller of the paid policy count and selected-policy limit; the source ceiling is the smaller of 16 times that count and the source-span limit.

The record counts are O(1) lengths of already paid private arrays, obtained before funding without new source/projection inspection. The 64-policy-visit ceiling conservatively covers filtering, grouping, conflict/rank passes and ID sorting under the kernel's 4,096-record limit. The renderer hashes the already computed resolution instead of resolving twice. These are logical-work units, not measured CPU comparisons or physical byte-copy counts. Large state can exhaust the unchanged original allowance. The current-state byte ceiling includes the same bounded temporal JSON growth allowance used by the validation cache. Rendering then runs inside `withAuthorityValidationSession`'s owner/write fence. Eligibility denial consumes a session attempt. The render operation settles after the actual fenced transaction commits. Failure retains the render charge; it cannot roll back funding or refund an attempt. The callback rechecks interruption, SQLite/write confidence and the next temporal boundary after rendering, and the method checks the original lease again before returning an artifact. Nested funding inside the eligibility transaction is prohibited.

The returned private artifact carries its render operation ID and charge. Original work/settlements remain in the journal; the artifact is not a serialized capability. A caller must still bind the complete actual request, trusted host input, selected policy artifact and source dependencies to supported count evidence, route and actual dispatch/delivery gates. Rendering can be repeated only by paying again under the same original allowance. A rolled-back eligibility callback invalidates cache/session reuse; a later funded retry requires fresh paid validation and cannot refresh the original episode limits.

## Verification and remaining integration

`--authority-policy-rendering-self-test` and `python3 scripts/test_authority_policy_rendering.py` use isolated synthetic stores and emit fixed booleans only. The focused runner passed 105 checks: 82 renderer/owner contracts and 23 genuine render-funding SIGKILL/two-restart checks. The matching-source optimized app passed 3,094 application checks. Counts overlap. Current bundle, source capture and verification evidence are recorded in [STATUS.md](STATUS.md).

Provider preparation must treat the complete rendered message as mandatory and count it before optional retrieval. Native consumers still need their own supported payload/count contract. Cross-project global policy evidence must remain in the complete dependency closure; the earlier work-binding restriction to episode-project dependencies cannot be used to discard it. Archives retain original policy operations and render accounting, but a dedicated durable complete render/input manifest contract is still needed. No live consumer accepts this artifact as permission.

The current preparation path requires the accepted episode binding to match current authority. A policy mutation makes that binding stale and refuses rendering. Rebuilding an already accepted request under changed policy still needs a separately immutable current prepared-work authority anchor, linked to the original acceptance and original allowance. It must preserve the accepted baseline, reject inactive or changed task selection, retain every prior charge and recount mandatory content. Reaccepting the same request as a new episode cannot be used to refresh its allowance. This anchor/rebuild contract belongs to the complete input-proof and shared-gate integration.
